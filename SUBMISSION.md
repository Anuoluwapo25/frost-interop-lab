# ZECATHON submission: FROST Interop Lab

**Track:** Core & Tooling

## One line

A conformance and interoperability test lab for Zcash FROST wallets: shared vectors, a plug-in adapter protocol, a report of which implementations actually work together, and a real Orchard spend signed by one FROST group whose shares live in three independent implementations.

## Why Core & Tooling

This is the unglamorous work the FROST wallets are built on. It doesn't compete with any of the six wallets; it lets all of them check their key derivation and backups against shared vectors and against each other, before a user finds out the hard way.

## The problem

FROST lets a group control shielded ZEC together, with no single member able to spend. At least six teams are building FROST wallets for Zcash: Zkool, Zafe, Konclave, Quorum, NoirWallet and OpenPGP Wallet. They share the FROST signing library, but each defines its own address derivation, signer messages and backups. One builder in the [October grant thread](https://forum.zcashcommunity.com/t/interoperable-frost-co-signing-for-shielded-zec-open-specs-and-a-reference-implementation/58172) put it this way: *"each wallet is defining its own coordinator-to-signer messages and its own share backups."*

The consequence is concrete. Two key derivations are in use today: legacy (ZF's `zcash-sign`) and ZIP 2005 `use_qsk` (Zafe, Zkool's newest groups). **For the same group they produce different addresses.** Restore a group in a wallet that uses the other derivation and it shows a zero balance.

A shared spec is being written. Until now nothing tested implementations against it or against each other, and nobody had shown signers from different implementations producing one valid Orchard spend.

## What we built

- **Shared vectors with sources recorded:**
  - 10 official Orchard key vectors for the legacy derivation
  - 8 ZIP 2005 `use_qsk` vectors from frost-tools#610
  - 17 `zkfrost` v1 backup cases (5 valid, 12 must-reject), generated by this lab from Zkool's format
- **An adapter protocol** ([ADAPTERS.md](ADAPTERS.md)): JSON lines over stdin/stdout, any language, a few dozen lines per wallet.
- **Differential testing:** every adapter gets the same seeded random inputs (valid Pallas points, random keys and backups), and every pair is compared. Backups are cross-decoded: A's string must restore in B.
- **Cross-implementation FROST signing:** the lab coordinates re-randomized FROST(Pallas, BLAKE2b-512) sessions whose shares are split between two implementations. It aggregates the shares, blames any bad one, and has every implementation verify the RedPallas signature. There are 10 verification vectors made with ZF's FROST and judged by the `orchard` crate, including a malleable `S + q`.
- **A real Orchard spend, end to end:**
  1. A 3-of-4 group is dealt, with one share each in Rust, Python and TypeScript.
  2. The `orchard` crate builds a bundle spending the group's note and creates the Halo2 proof.
  3. The group signs the bundle's ZIP 244 digest with the spend's randomizer.
  4. `orchard`'s `BatchValidator` accepts the proof, the group's spend authorization and the binding signature.
- **Reports:** Markdown, JSON and a standalone HTML compatibility matrix. The CI exit code fails on any incompatible pair, and there's a GitHub Actions workflow.
- **Four adapters:**
  - a TypeScript reference whose BLAKE2b, BLAKE3, Pallas and bech32m are written from the specs, with no dependencies
  - an independent Python standard-library implementation
  - an adapter on the official crates: `orchard` + `zcash_keys`, and ZF's `reddsa` FROST with `frost-rerandomized` (the stack `zcash-sign` uses)
  - a deliberately broken example with four realistic bugs

## Results

- The official `orchard` + `zcash_keys` crates pass every vector, including the ZIP 2005 default addresses and UFVKs, and agree with both of our implementations on 200 random cases per derivation (built and run in GitHub Actions).
- The TypeScript and Python implementations pass every vector and agree on every random case. With Zafe's own checker, that makes four independent implementations agreeing on the ZIP 2005 vectors.
- **Signing:**
  - ZF's Rust FROST, our Python and our TypeScript sign together in every combination: 100 of 100 random mixed groups per pair (2 ≤ t ≤ n ≤ 5, either side dealing).
  - Every result verifies under the `orchard` crate's verifier and both of ours.
- **End to end:** the `orchard` crate validates the mixed group's Orchard spend: proof, spend authorization and binding signature. A wrong signature is rejected; that negative control is a test.
- **The broken example is caught on all four bugs:**
  - `rivk` reduced mod p instead of q: fails 8 of 8 vectors and 100 of 100 random cases.
  - A backup decoder accepting invalid participant IDs.
  - A signer that ignores the randomizer: its share is blamed by name before anything reaches the transaction.
  - A verifier that accepts non-canonical `S`.
- The derivation split is demonstrated: the same group gives a different `rivk`, and so a different address, under legacy and ZIP 2005.

## Try it

```sh
npm test        # unit tests, mixed-group signing, the Orchard spend, a lab run
npm run demo    # the story in five steps
node src/cli.ts spend            # a 3-of-4 group across Rust, Python and TypeScript spends an Orchard note
node src/cli.ts run --fuzz 100   # writes reports/report.html
```

Node 22.18+ and Python 3, with nothing to install. Rust is needed for the `orchard-rust` adapter: `cd adapters/orchard-rust && cargo build --release`.

## Honest limitations

- The ZIP 2005 vectors are not yet official ZIP vectors.
- The backup vectors haven't been checked against Zkool's binary.
- The Orchard spend is fully validated by the `orchard` crate but not broadcast: the note is in a locally built commitment tree, not on chain.
- Keys come from a trusted dealer, not DKG.
- No real wallet's code is wired in yet; the three agreeing implementations are libraries.
